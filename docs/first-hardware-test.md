# First PP-100 hardware test

This is a validation procedure, not a claim that the utility has been tested against a physical PP-100. All bundled example data is explicitly simulated.

1. Download the ZIP from the latest successful **Windows build and test** Actions run. Extract the outer artifact ZIP and then the application ZIP. Run `DiscproducerDiagnostics.App.exe` on Windows 11 x64. No separate .NET runtime is required.
2. Keep Epson's official driver and Total Disc Maker installed. Connect and power on the PP-100; wait until normal publishing is idle. Leave Simulation mode **off**.
3. Click **Scan for Devices**. Select the row exposing the USB printer interface; confirm actual VID/PID and the instance/parent paths against Device Manager. Multiple rows may be one composite device. If several physical devices are present, explicitly select the intended one.
4. In **USB Interfaces**, click **Inspect descriptors**. Expand the tree. Device/configuration/string/endpoint values must have descriptor provenance. Check hub-port driver-key validation errors if retrieval fails. A visible endpoint is not proof of an accessible application transport. Active configuration remains unavailable because this release does not send GET_CONFIGURATION.
5. Click **Connect**. This performs a shared read-only handle probe and the existing identity/status sequence. Opening the handle, receiving a driver response, parsing it, and proving a physical bus acknowledgement are separate facts. The application never claims the last from an API reply.
6. Click **Run Full Diagnostics**. It re-enumerates the selected device, inspects descriptors/drivers, reads printer queues/jobs, attempts only allowlisted identity/status requests, records failures/skips, and opens an export dialog. A per-operation timeout or unsupported interface does not authorize a different driver or speculative command. If collection is cancelled, export the accumulated evidence manually.
7. Save **TechnicalDiagnostics** first. It omits serials, identifiers, job names and raw payloads. Choose **FullForensic** only if you intend to share raw responses and any imported capture; read and accept the explicit privacy confirmation. The report distinguishes API invocation, valid/interpreted response, interface opening and unknown wire acknowledgement.
8. In **Protocol Explorer**, select GET_DEVICE_ID or GET_PORT_STATUS and execute individually if more evidence is needed. In **Communication Log**, select the resulting transaction and inspect request/response, native error, timeout and interpretation. Empty IOCTL input is genuine; the app does not invent USB setup bytes for usbprint.sys calls.
9. In **Windows Printer**, inspect driver/version, port monitor, jobs and association evidence. A queue is associated only through matching PnP instance/ancestry or a usable container ID. An uncorrelated/ambiguous queue must not be treated as the selected printer's hardware status.
10. While the printer is idle, disconnect USB and explicitly refresh to verify removal handling; reconnect, rescan and reconnect. Confirm Total Disc Maker still works with unchanged driver/configuration. Export before closing; raw session data is not automatically persisted.

Record exact model/firmware (from authoritative labels/software), Windows version, Epson driver/version, actual VID/PID, interface path, query outcomes, returned byte counts and native errors. Do not replace missing evidence with a mock run. If identity/status fails, proceed to the [passive capture guide](usb-capture.md), not EEPROM or reset commands.
